# MCP OAuth Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** MCP clients sign in to `/api/mcp` through the browser (OAuth 2.1) while `rmk_` keys keep working.

**Architecture:** Better Auth's `jwt()`, `mcp()` and `cimd()` plugins make the app an OAuth 2.1
authorization server. `/api/mcp` dispatches on the bearer: `rmk_` keys take the existing path,
anything else goes through `requireMcpAuth` plus a live-consent check. A consent page and a
"Connected apps" section complete the flow; the plugin drops its env-var requirement.

**Tech Stack:** Next.js 16 route handlers, Better Auth 1.7.7 (`@better-auth/mcp`, `@better-auth/cimd`),
Drizzle + PGlite tests, MCP SDK v1, tRPC, next-intl.

**Spec:** `docs/superpowers/specs/2026-10-06-mcp-oauth-design.md`

## Global Constraints

- Resource identifier: `${BETTER_AUTH_URL}/api/mcp`; login page `/login`; consent page `/oauth/consent`.
- `rmk_` bearer behaviour on `/api/mcp` and all of `/api/v1` is unchanged.
- OAuth agent-run credential id: `oauth:<userId>:<clientId>`.
- Audit kinds added: `oauth-consented`, `oauth-denied`, `oauth-revoked`.
- Plugin `userConfig.roadmap_url` default `https://roadmap.slne.dev`; plugin version 1.3.0.
- UI strings in `messages/en` and `messages/de`.

## Review Focus

- A token whose consent was revoked → 401 with `WWW-Authenticate` (Task 3 test).
- A token for a user removed from the allowlist → 401 (Task 3 test).
- A bearer that is neither a key nor a valid JWT → 401 with the challenge, not a 500 (Task 3 test).
- A tampered or expired consent query → error page, no grant (Task 4 test).
- `/.well-known/*` without a session → metadata JSON, never the `/login` redirect (Task 2 test).

### Task 3: `/api/mcp` accepts OAuth tokens

**Files:** Create `src/lib/auth/mcp-auth.ts` (+ test), modify `src/app/api/mcp/route.ts`, `route.test.ts`.

**Produces:** `mcpCredential(request, verify): Promise<{ actor, credentialId } | null>` where
`verify` is the verified claims `{ sub, azp | client_id }`; `consentExists(db, userId, clientId)`.

- [ ] Tests: `rmk_` bearer keeps today's behaviour (existing tests); a non-`rmk_` bearer without a valid
  token → 401 with `WWW-Authenticate`; valid claims with consent and provisioned user → tool call

- [ ] Route: `rmk_` → existing `bearerAuth` path; else `requireMcpAuth(getAuth(), handler, { resource: mcpResource() })`
  whose handler resolves the actor from claims, checks consent, then serves MCP.
- [ ] Commit `feat(mcp): accept OAuth access tokens`.
